## Slide 4 — 1.1 项目背景与问题定义

> 顶部导航：**研究背景** · 核心设计 · 实现与测试 · 总结展望

四象限要点：

- **Linux ABI 兼容的生态要求**
  Asterinas / RustOS 若要支撑真实开发者工具链，不能只运行普通程序，还必须支持 GDB、strace 等调试工具。
- **调试能力不是单一 syscall**
  进程调试涉及进程管理、信号、wait、地址空间、寄存器上下文、安全策略和 procfs，是一条完整的数据 / 控制通路。
- **核心问题**
  如何在此前没有 ptrace 设施的 RustOS 中，构建足够 Linux 兼容、足够安全、并能支撑真实调试器运行的进程调试子系统。
- **内核视角**
  需要补齐：追踪关系管理、执行流停止 / 恢复、异常到信号转换、跨地址空间访问、wait 状态编码、架构寄存器 ABI。

> **目标**：让真实 GDB / strace 能在 Asterinas 上原生运行并调试用户进程。

## Slide 5 — 1.2 总体目标与验收标准

四项总体目标：

- **ptrace 核心 ABI** — 支持 GDB 的断点、停止、寄存器 / 内存读写、单步与继续；支持 strace 的 syscall entry/exit。
- **procfs 调试接口** — 提供 `/proc/<pid>/maps`、`/proc/<pid>/mem`、`/proc/<tid>`、`/proc/<pid>/auxv` 等接口。
- **安全边界** — 对齐 `ptrace_may_access`，并引入 Yama LSM 的 `ptrace_scope` 策略。
- **真实工具链验证** — 以真实 GDB、strace、gVisor ptrace 测试、回归测试和安全测试作为验收依据。

**验收标准清单**

| # | 验收标准 |
|---|---|
| 1 | GDB 能启动并调试单线程用户程序 |
| 2 | GDB 能设置软件断点，命中 `int3` 后进入 stop |
| 3 | GDB 能读取 / 修改通用寄存器 |
| 4 | GDB 能读取 / 修改用户进程内存 |
| 5 | GDB 能单步执行并继续执行 |

| 9 | Yama `ptrace_scope` 能限制非亲缘或无权限访问 |
| 10 | 相关功能纳入 CI 与回归测试 |

## Slide 6 — 1.3 需求拆解：从调试动作到内核能力

## Slide 8 — 2.1 总体架构：七层调试能力通路

> 配图：`gdb_initial_source_analysis_assets/01_module_map.png`（模块关系图）

从用户态到内核的七条协作链路（图中节点对应源码模块）：

1. **用户态** GDB / strace —— 发起 `ptrace(2)` 与 `/proc` 读写
2. **系统调用入口** `sys_ptrace` —— `kernel/src/syscall/ptrace.rs`
3. **权限检查** —— `alien_access.rs` + Yama LSM
4. **Tracer / Tracee 状态机** —— `process/posix_thread/ptrace`
5. **wait/waitpid 报告** —— `TraceeStop` / `TraceeExit`
6. **远程内存 / 寄存器** —— `read_alien`/`write_alien`、`CUserRegsStruct` / USER area
7. **procfs 视图** —— `/proc/[pid]/{mem,cmdline,environ,auxv,maps}`

> 事件协作（syscall / signal / exec / exit / clone）统一触发 ptrace-stop；procfs 复用 VMAR alien 访问与权限检查。

## Slide 9 — 2.2 关键设计取舍：复用内核既有语义

- **停止收敛点** — 以信号投递点作为 ptrace-stop 的统一入口，断点、单步、普通信号和 event 共享同一停止路径（`ptrace_stop` / `do_ptrace_stop`，`ptrace/mod.rs:385`）。
- **关系维护** — tracer 通过 `tracees` map 的 **`Arc`** 强引用持有 tracee；tracee 通过 `TraceeState.tracer` 的 **`Weak`** 反向指向 tracer，单向 `Weak` 打破强引用环；并以固定锁序避免死锁。
- **资源访问** — 通过 VMAR alien access 访问目标地址空间，统一支撑 ptrace `PEEK`/`POKE` 与 `/proc/pid/mem`（`vmar_impls/access_alien.rs`）。
- **架构解耦** — x86-64 `user_regs_struct`、`RFLAGS.TF`、USER area 等 ABI 细节下沉至 `arch/x86/ptrace.rs`。

> **设计原则**：把高风险调试能力收束为显式状态机、显式访问原语和显式安全检查。

## Slide 10 — 2.3 ptrace 系统调用入口：从 Linux request 到内核对象方法

> 配图可选：`gdb_initial_source_analysis_assets/02_ptrace_dispatch.png`（请求分发图）

四步分发（`kernel/src/syscall/ptrace.rs:21`）：

1. **request 编号解析** — `PtraceRequest::try_from(request)`，非法值返回 `EIO`
2. **定位 tracee** — `current.get_tracee(tid)`，校验当前 tracer 是否跟踪该 tid
3. **处理用户指针** — `read_val` / `write_val` 在 `addr`/`data` 与用户空间间搬运
4. **委托 ptrace 核心层** — `PosixThread::ptrace_xxx(...)`

```text
sys_ptrace(request, tid, addr, data)
    ├── PTRACE_TRACEME / CONT / GETREGS / ...
    ├── current.get_tracee(tid) → tracee
    ├── read_val(data) / write_val(data, &val)
    └── tracee.ptrace_xxx(...)
```

**关键取舍**
- 避免 `sys_ptrace` 同时理解 wait、信号、寄存器与地址空间细节
- Linux ABI 语义被翻译为内核对象操作
- `PEEK` 返回值、`POKE` 数据参数、`GET`/`SET` 用户指针分别处理

> **核心不变量：入口薄，状态机厚。**

## Slide 11 — 2.4 tracer / tracee 关系：Weak 引用、tracees map 与锁序

```rust
struct PosixThread {
    // “我是否被追踪”：停止原因 + 寄存器快照
    tracee_status: Once<TraceeStatus>,
    // “我追踪哪些线程”：tid -> 强引用的 tracee
    tracees: Once<Mutex<BTreeMap<Tid, Arc<Thread>>>>,
}

pub(super) struct TraceeStatus {
    is_stopped: AtomicBool,
    state: Mutex<TraceeState>,   // tracer(Weak) / signal / event / options / regs
}
```

- **`tracee_status`** — 记录「我是否被追踪」；保存停止原因与寄存器快照；供 resume / wait / exit 协同。
- **`tracees` map** — 记录「我追踪哪些线程」；wait 遍历可报告 tracee；**持有 `Arc<Thread>` 强引用**。
- **`Weak` 在哪？** — 反向的 `TraceeState.tracer: Weak<Thread>`（`ptrace/mod.rs:719`）。tracer→tracee 用 `Arc`、tracee→tracer 用 `Weak`，单向 `Weak` 打破循环强引用。
- **锁序约束** — 固定为 `tracer.tracees → tracee.tracee_status`（见 `attach_to`/`clear_tracees` 注释，`ptrace/mod.rs:275,315`）。wait、resume、detach、exit 清理均按同一方向访问，避免 tracer 遍历与 tracee 停止 / 退出之间的交叉等待。

## Slide 12 — 2.5 ptrace-stop 主状态机：保存现场、通知 tracer、阻塞 tracee、恢复现场

> 配图：`gdb_initial_source_analysis_assets/03_state_machine.png`（状态机）

**`do_ptrace_stop()` 顺序**（`ptrace/mod.rs:466`）：

1. 保存寄存器现场（`general_regs = *user_ctx.general_regs()`，记录 `orig_syscall_ret`）
2. 记录停止信号 / 事件与 wait status（`state.signal.stop(...)`）
3. 向 tracer 投递 `SIGCHLD(CLD_TRAPPED)`，并唤醒其 `children_wait_queue`
4. tracee 以 `PauseReason::StopByPtrace` 阻塞（`Waiter::pause_until_by`）
5. resume 后回写寄存器（`*user_ctx.general_regs_mut() = regs`）并返回执行路径

**核心价值**
ptrace-stop 不另造独立调度语义，而是复用 signal 与 wait。这样 GDB / strace 看到的就是 Linux 风格的 `wait4` 状态字。若中途被 `SIGKILL` 打断，则清空快照并返回 `Interrupted`。

## Slide 13 — 2.6 resume 语义：CONT、SINGLESTEP、SYSCALL 的统一恢复接口

```rust
pub enum PtraceContRequest {
    Continue(Option<SigNum>),
    SingleStep(Option<SigNum>),
    Syscall(Option<SigNum>),
}
```

| 恢复 request | 信号处理 | x86 TF 位 | syscall tracing | 用途 |
|---|---|---|---|---|
| `PTRACE_CONT` | 注入 / 抑制 | 清除 | 关闭 | 普通继续 |
| `PTRACE_SINGLESTEP` | 注入 / 抑制 | 设置 | 关闭 | GDB 单步 |
| `PTRACE_SYSCALL` | 注入 / 抑制 | 清除 | 开启 | strace 跟踪 |

**`resume()` 核心动作**（`ptrace/mod.rs:580`）
- 替换或清空 `StopDeliverySignal`（`inject` / `clear`）
- 设置 / 清除 `RFLAGS.TF`（`enable_single_step` / `disable_single_step`）
- 打开 / 关闭 `is_tracing_syscall`
- 清除 `is_stopped` 并唤醒 tracee（`wake_signalled_waker`）

## Slide 14 — 2.7 StopDeliverySignal：区分 Pending、Consumed、Injected、Empty

```rust
#[derive(Default)]
pub(super) enum StopDeliverySignal {
    Pending(DequeuedSignal, PtraceWaitStatus),  // 等待 wait 观察
    Consumed(DequeuedSignal),                   // wait 已报告
    Injected(DequeuedSignal),                   // resume 注入新信号
    #[default] Empty,                           // 信号被抑制 / 清理
}
```

| 状态 | 含义 |
|---|---|
| `Pending` | 等待 wait 观察 |
| `Consumed` | wait 已报告，但信号尚未投递 |
| `Injected` | resume 时 tracer 注入 / 替换的新信号 |
| `Empty` | 信号被抑制或已清理 |

**为什么需要四态？**（`ptrace/util.rs:51`）
- 同一 ptrace-stop 不能被 wait 重复报告（`Pending`→`Consumed`，`WNOWAIT` 时保持 `Pending`）
- wait 返回后信号不能立刻丢弃
- tracer 仍可在 `PTRACE_CONT(pid, 0, sig)` 时替换、注入或抑制信号

## Slide 15 — 2.8 信号投递停：在 signal delivery 之前给 tracer 裁决机会

流程（`ptrace_stop` → `do_ptrace_stop`）：

`pending signal 出队` → `非 SIGKILL 且被追踪` → `ptrace_stop()` → `tracer wait/resume` → `投递 / 替换 / 抑制`

| `PtraceStopResult` | 含义 | 信号管线动作 |
|---|---|---|
| `Continued(Some)` | 允许或替换信号 | 查询 action 并投递 |
| `Continued(None)` | 抑制信号 | 直接返回 |
| `Interrupted` | 被 `SIGKILL` 打断 | 重新处理 `SIGKILL` / 退出 |
| `NotTraced(Some)` | 未被追踪 | 走普通信号路径 |

> 关键：把「是否投递、投递哪个信号」的裁决点放在信号真正进入 handler 之前，调试器因此可以观察、替换或吞掉每一个信号。

## Slide 16 — 2.9 系统调用停：在 task 主循环中布置 entry / exit 双检查点

```text
ReturnReason::UserSyscall                         // kernel/src/thread/task.rs:87
    ├── orig_syscall_ret = Some(user_ctx.syscall_ret())
    ├── ptrace_may_stop_on_syscall()   // entry-stop
    ├── if !Interrupted: handle_syscall()          // 真正执行 syscall
    └──                  ptrace_may_stop_on_syscall()   // exit-stop
```

**TRACESYSGOOD**（`ptrace/util.rs:219`）
- 普通 syscall-stop 使用 `SIGTRAP`
- 开启 `PTRACE_O_TRACESYSGOOD` 后编码为 `SIGTRAP | 0x80`
- strace 可据此区分 syscall-stop 与断点 `SIGTRAP`

**关键细节**
若 entry-stop 被 `SIGKILL` 打断（返回 `Interrupted`），则**不继续执行系统调用**；否则先执行 syscall，再做 exit-stop。`orig_syscall_ret` 保存 syscall 入口快照（`ThreadLocal`，`Cell<Option<usize>>`），支撑 x86-64 `orig_rax` ABI。

## Slide 17 — 2.10 event-stop：以 PtraceOptions 控制 exec / exit 等事件是否报告

可配置的事件选项（`PtraceOptions`，`ptrace/util.rs:128`）：

`TRACEEXEC` · `TRACEEXIT` · `TRACEFORK` · `TRACEVFORK` · `TRACECLONE` · `TRACEVFORKDONE` · `EXITKILL` · `TRACESYSGOOD`

判定流程：`tracee 有 tracer?` → `option 已开启?` → `构造 event + siginfo` → `进入 do_ptrace_stop()` → `GETEVENTMSG 读取 message`

**exec 兼容语义**
即使未开启 `TRACEEXEC`，成功 `execve` 后也应发送普通 `SIGTRAP`，让调试器在新程序开始执行前接管（`ptrace/mod.rs:421`，对齐 `ptrace(2)` man page）。

**当前边界**
已支持 `EXEC` / `EXIT`；`fork` / `vfork` / `clone` family 的 event-stop 仍属后续扩展范围——会触发 clone-family event 的 clone 调用当前被拒绝（`needs_clone_stop`，`ptrace/mod.rs:537`）。

## Slide 18 — 2.11 wait / waitpid 整合：tracee stop 优先于普通 child stop

```rust
enum WaitStatus {
    Zombie(...), Stop(...), Continue(...),
    TraceeExit(Arc<Thread>),
    TraceeStop(Arc<Thread>, PtraceWaitStatus),
}

// do_wait(): try_wait_tracees() → try_wait_children()
```

**设计要点**
- tracee 状态先以 ptrace 语义报告（`try_wait_tracees` 先于 `try_wait_children`）
- 普通 child wait 跳过 `is_traced()`
- ptrace-stop 不要求 `WSTOPPED`
- main thread 退出但进程未 zombie 时延迟报告，避免重复

**wait status 编码**
`PtraceWaitStatus` 最终编码为 `wait4 status = ((si_status as u32) << 8) | 0x7f`（`ptrace/util.rs:227`）；`si_status` 可为普通信号、`SIGTRAP|0x80`，或带 event code 的高位编码（`SIGTRAP | (event_code << 8)`）。

## Slide 19 — 2.12 跨进程内存访问：VMAR alien access，而不是切换页表

> 配图：`gdb_initial_source_analysis_assets/04_memory_access.png`（内存访问）

- **统一访问原语** — `read_alien` / `write_alien` / `fill_zeros_alien` 收敛到 `access_alien()`，统一处理地址校验、按页遍历、缺页与竞态（`vmar_impls/access_alien.rs:91`）。
- **接口复用** — `PTRACE_PEEK/POKE_TEXT/DATA` 与 `/proc/<pid>/mem` 共享 alien access；`/proc/<pid>/maps` 遍历 VMAR 输出映射。
- **工程意义** — 通过 `query_page_with_required_flags` 在目标 `VmSpace` 上直接按页取 `UFrame`，**无需切换到目标页表**；必要时以 `handle_page_fault(... .force())` 触发缺页后重试；跨进程读写封装在 `VmReader`/`VmWriter` 与权限检查边界内。

## Slide 20 — 2.13 /proc/<pid>/maps 与 /proc/<pid>/mem：提供 Linux 式进程视图

| 接口 | 访问对象 | 访问强度（kind） | 凭证（creds） |
|---|---|---|---|
| `/proc/<pid>/maps` | 地址空间布局元数据 | `Read` | `READ_WITH_FS_CREDS` |
| `/proc/<pid>/mem` read | 用户虚拟内存内容 | `Attach` | `ATTACH_WITH_FS_CREDS` |
| `/proc/<pid>/mem` write | 用户虚拟内存修改（force write 支撑断点） | `Attach` | `ATTACH_WITH_FS_CREDS` |
| ptrace `PEEK`/`POKE` | stopped tracee 的一个 word | `Attach` | `ATTACH_WITH_REAL_CREDS` + 已建立追踪关系 |

- **maps** — 遍历目标 VMAR 输出可执行文件、共享库、栈、堆、匿名映射等布局，帮助 GDB 定位代码和数据（`procfs/pid/task/maps.rs`）。
- **mem** — 以 seek/read/write 文件接口暴露目标地址空间，并在权限满足时允许 force-write 只读代码映射中的 `int3`（`procfs/pid/task/mem.rs`）。

## Slide 21 — 2.14 x86-64 寄存器 ABI：CUserRegsStruct、USER area 与字段级写策略

> 配图可选：`gdb_initial_source_analysis_assets/05_register_snapshot.png`（寄存器快照）

| 字段类别 | 写策略（`Policy`） | 设计理由 |
|---|---|---|
| 通用寄存器 `rax..r15` | `Set` | 调试器可自由修改 |
| `rip` / `rsp` | `SetIf(is_user_addr)` | 防止跳到内核地址 |
| `fsbase` / `gsbase` | `SetIf(is_user_addr)` | TLS 基址不可指向内核 |
| `rflags` | `SetBitsTruncate(mask)` | 只允许用户态可控位 |
| `cs/ss/ds/es/fs/gs` | `Fixed` | 匹配 Linux ABI，保持段不变量 |
| debug registers | 读默认值；写 `EOPNOTSUPP` | 满足 GDB 探测，不支持硬件断点 |

**单步与 USER area**（`arch/x86/ptrace.rs`）
`PTRACE_SINGLESTEP` 设置 `RFLAGS.TF`；执行一条指令后 `#DB` → `SIGTRAP(TRAP_TRACE)` → ptrace-stop。`PEEKUSER`/`POKEUSER` 通过 offset 访问 `CUserRegsStruct`（`read_user_word`/`write_user_word`），并额外处理 `orig_rax`、`fsbase`/`gsbase` 与 debug registers（`DR6` 读默认 `0xffff0ff0`，写返回 `EOPNOTSUPP`）。

## Slide 22 — 2.15 断点闭环：从 GDB 写 int3 到恢复原指令

完整闭环（无独立断点模块，全部由既有原语组合）：

1. `maps` 定位代码映射 →
2. `PEEKTEXT` 读取原指令 →
3. `POKETEXT` 写 `int3` →
4. `#BP` → `SIGTRAP` →
5. `ptrace_stop` 保存现场 →
6. wait 返回 `SIGTRAP` →
7. GDB 读 / 改寄存器 →
8. 修正 `RIP` →
9. 恢复原指令 →
10. `SINGLESTEP` 执行一次 →
11. 重新插入 `int3` →
12. `CONT` 继续

**不是单独模块**
软件断点依赖 `POKE` 写代码页、异常到 `SIGTRAP`、ptrace-stop、wait 编码、`GET`/`SETREGS` 与 `SINGLESTEP` 的组合。

**为什么需要单步**
恢复原指令后必须执行一次真实指令，再重新插入 `int3`；否则同一地址会反复命中断点。

## Slide 23 — 2.16 与 Rust 安全模型的关系：把危险能力收束在显式边界上

**寄存器机制 → 实现要点 → 安全约束**

| 寄存器机制 | 实现要点 | 安全约束 |
|---|---|---|
| `CUserRegsStruct` | 镜像 Linux x86-64 `user_regs_struct` | 作为 GDB `info registers` 的 ABI 基础 |
| `REG_RULES` | `Set` / `SetIf` / `SetBitsTruncate` / `Fixed` 字段策略 | 限制非法 `RIP`/`FS`/`GS`/`RFLAGS` 写入 |
| USER area | `PEEKUSER`/`POKEUSER` 按偏移读写；debug registers 读默认值 | `DR0–DR7` 写入暂返回 `EOPNOTSUPP` |
| `SINGLESTEP` | 设置 `RFLAGS.TF`；`#DB` 转 `SIGTRAP(TRAP_TRACE)` | 单步后再次进入 ptrace-stop |

**Yama `ptrace_scope`**（`security/lsm/modules/yama.rs`）

| scope | 语义 |
|---|---|
| `0` Disabled | 不附加额外限制 |
| `1` Relational（默认） | 仅祖先进程或 `CAP_SYS_PTRACE` 可 attach |
| `2` Capability | 仅 `CAP_SYS_PTRACE` 可 attach |
| `3` NoAttach | 任何进程都不可 attach；**一旦设置不可再降低** |

> - `ptrace_may_access`：同进程放行 → UID/GID 检查 → `CAP_SYS_PTRACE` → LSM hook
> - 不同入口区分 `Read`/`Attach` 与 `FsCreds`/`RealCreds`，降低 procfs 绕过风险

## Slide 29 — 4.1 风险分析与后续路线

| 主要风险 | 具体表现 | 后续路线 |
|---|---|---|
| stop/resume 竞态 | tracee 停止、tracer wait、resume、exit 之间可能竞态 | 并发压力测试与不变量梳理 |
| 锁序风险 | `tracees` map、`tracee_status`、信号队列、wait queue 锁交错 | 固定锁序与路径审计 |
| ABI 细节风险 | GDB 对寄存器布局、段选择子、debug registers、personality 敏感 | 补齐 regset、FP/SIMD、`DR0–DR7` |
| 安全绕过风险 | ptrace 与 procfs 若检查不统一可能出现绕过 | 统一 access mode；补 dumpable、`PR_SET_PTRACER` |
| 多线程 / 架构扩展 | clone event-stop 与非 x86 寄存器 ABI 尚不完整 | 支持 fork/vfork/clone；推广到 riscv64/loongarch64 |

## Slide 30 — 4.2 总结：从能跑 GDB 到调试能力骨架

- **设计核心** — 以 ptrace-stop 状态机为中心，把信号、异常、系统调用、wait、寄存器、跨进程内存访问和安全策略统一到一条 Linux ABI 兼容的调试路径中。
- **实现路径** — 先落地 `/proc/pid/maps` 和 `/proc/pid/mem`，再实现 alien access 与安全检查；随后建立 ptrace syscall、stop/wait/resume 闭环，并补齐寄存器、单步、断点、options、event-stop、syscall-stop。
- **项目价值** — 不仅是「能跑 GDB」，更为 RustOS 建立了跨越多个内核子系统的调试能力骨架，也成为检验进程、内存、信号和安全模型正确性的综合压力测试入口。
