# PART 1　研究背景与目标
### 进程调试的意义与内核能力需求

## 第 4 页 — 1.1 研究背景与问题定义

Asterinas 是由北京大学、中关村实验室、蚂蚁集团联合发起的一个用 Rust 编写、与 Linux ABI 兼容的国产自主可控安全操作系统内核，能直接运行 Linux 程序，并借助框内核架构提升内核可靠性。

一个面向开发者的操作系统，不能只满足于把程序跑起来，还要支撑起程序开发的完整闭环，而**进程调试**正是其中最基础的一环。无论是排查应用逻辑的上层开发者，还是分析系统调用、内存与寄存器行为的底层开发者，都离不开用户态进程调试机制。同时，一个新内核要真正可用，关键在于能**直接复用现有的用户态生态**，而不是要求应用重写；而 Linux ABI 已是事实标准，唯有兼容它，才能直接复用海量现有调试工具链生态，如 GDB strace 等。

因此，在 Asterinas 上支持用户进程调试，本质上就是**兼容 Linux 的 ptrace 接口与相关配套机制**——而这不是单个系统调用，而是贯穿进程管理、信号、wait、地址空间、寄存器、安全与 procfs 的完整通路。

## 第 5 页 — 1.2 案例研究：调试的基本需求——以断点为例

调试器对内核的基本需求：
 - 运行时暂停目标进程工作
 - 读写目标进程的私有状态（寄存器、内存、控制流 ...）
 - 调试结束后恢复目标进程正常运行

以最常用的「GDB 软件断点」为例，一次命中并恢复，需要内核按下图配合：

![断点案例](assets/09_breakpoint_loop.png)

- 这些功能分别需要：跨进程改内存、异常转信号、停 / 等 / 恢复、读写寄存器、单步，正是要逐一构建的内核能力。

## 第 6 页 — 1.3 Linux 为调试器提供的抽象：调试能力通路

![调试能力通路](assets/01_arch_overview.png)

Linux 暴露给 GDB 等调试器的抽象如图所示：用户工具发出请求，经系统调用接口进入内核，先过权限检查鉴权放行，再交给 ptrace 核心状态机。状态机是整条通路的中枢，负责建立关系、进入 ptrace-stop、向 tracer 报告 wait、再 resume 继续，一旦命中新的停止条件就再次回到 stop。
围绕这个中枢，向下分出三类能力：跨进程用户空间读写、寄存器上下文快照、以及与 signal / wait / exec / exit / clone 等系统调用的协作。

忠实构建相应抽象，才能正确复用 Linux 海量调试器生态。

---

## 第 7 页 — 1.4 总体目标与对应内核能力

要让开发者能使用 GDB / strace 调试用户程序，内核必须补齐的能力有：

| 总体目标 | 对应内核能力 |
|---|---|
| GDB 调试 | 建立 tracer / tracee 关系，使能 tracee 陷入内核 stop，并等待 tracer wait & resume |
| 设置并命中软件断点 | 使能修改只读内存写入 breakpoint，#BP 异常后进入 ptrace-stop |
| 读 / 写寄存器 | tracee stop 时保存 register 现场，按字段规则安全读写 |
| 读 / 写进程内存 | 跨进程安全读写目标地址空间，必要时主动触发 page fault |
| 继续 / 单步 | resume 继续，按需设置 CPU trap flag (TF) 单步执行 |
| strace 跟踪系统调用 | 在每次 syscall entry / exit 进入 ptrace-stop |
| 按安全策略限制调试 | 校验 uid/gid、CAP_SYS_PTRACE、Yama，拦截越权 attach |

## 第 8 页 — 1.5 相关工作：其它 OS 的调试路线对比

> 备注：各类从零或新架构的 OS 都在补调试能力，但接入调试器的技术路线差别很大，多数并未直接复用未经修改的 Linux 工具链。下表对比它们的内核调试接口与调试器接入方式。
> 备注：Redox OS——刻意不在内核实现 Linux ptrace，而是提供一个类 /proc 的 proc scheme 文件接口；并用 Rust 自写了一个 gdbserver，GDB 通过 Redox 的 IPC 走 GDB 远程串行协议连接，relibc 里另有一个尽力而为的用户态 ptrace 兼容层。所以 Redox 的 GDB 根本不经过 ptrace 系统调用。
> 备注：SerenityOS——实现了自己的 ptrace 系统调用，但语义并非 Linux ABI；要让 GDB 工作，需要给 GDB 新增一个 serenity target 后端（移植工作），而不是直接用未经修改的上游 GDB。它还自带一个原生调试器 sdb。
> 备注：Fuchsia / Zircon——微内核，无 ptrace；调试由跑在开发机上的 zxdb 客户端连接目标设备上的 debug_agent 组件完成，基于 Zircon 内核对象 koid 与 job/process 模型，且只能远程调试、不能自托管。
> 备注：Haiku——使用端口式（port-based）调试 API（install_team_debugger、team/thread 调试上下文），不是 ptrace；2024 年 GSoC 把 GDB 15.1 移植上来，后端把 Haiku 的调试端口事件翻译成 gdbserver 语义，并为此修改内核以暴露更多调试信息。
> 备注：对比之下，Asterinas 在内核里原生实现 Linux ptrace ABI，未经修改的上游 GDB / strace 用它们标准的 Linux 后端即可直接运行——无需自写或移植 gdbserver、无需远程 agent、无需为私有接口改造 GDB、无需用户态兼容层。
> 备注：Q&A 防线（gVisor）：若被问到 gVisor，它确实也在内部实现了 Linux ptrace（Sentry 的 pkg/sentry/kernel/ptrace.go），属同一路线；但 gVisor 是跑在宿主 Linux 之上的用户态沙箱运行时（Go），且只实现了跑容器够用的 ptrace 子集（历史上 gdb 与 strace 不能同跟一个进程）。因此稳妥表述是：在从零做的通用 OS 中，原生实现 Linux ptrace、直接复用未改 GDB/strace 的，Asterinas 是其中唯一一个。

| 系统 | 内核调试接口 | 调试器如何接入 |
|---|---|---|
| Redox OS | proc scheme，非 ptrace | 自写 Rust gdbserver，GDB 走远程协议 |
| SerenityOS | 自有 ptrace，非 Linux ABI | 移植 GDB，新增 serenity target 后端 |
| Fuchsia / Zircon | 内核对象模型，无 ptrace | zxdb 客户端连 debug_agent，仅远程调试 |
| Haiku | 端口式调试 API，非 ptrace | 移植 GDB，翻译到 Haiku 调试端口 |
| **Asterinas（本项目）** | **内核原生 Linux ptrace ABI** | **未经修改的上游 GDB / strace 直接运行** |

> 多数方案要么自定义协议、配自写或移植的 gdbserver / agent，要么为私有接口改造 GDB；在内核里原生实现 Linux ptrace、让未改的 GDB / strace 直接跑通的是少数——这正是本项目的技术取舍。

# PART 2　设计与实现
### ptrace 子系统的关键机制，以及与 Linux 的结构性差异

---

## 第 10 页 — 2.1 要解决什么问题：相同接口，内部更优的实现

对外语义与 ABI 必须对齐 Linux，工作落在内部结构与实现质量。借助框内核 + 安全 Rust 这个载体，几处关键机制做得与 Linux 不同：

- **跟踪关系是旁路 map，不动进程树**：Linux 把 tracee reparent 进全局进程树，attach / detach / exit 须全程持有全局写锁 `tasklist_lock`；本项目用一张旁路 `tracees` map，关系变更只落在两把文档化锁序的 per-object 锁上。
- **寄存器快照，而非原地编辑内核栈**：Linux 直接读写 tracee 内核栈上的 `pt_regs`，须先用 `wait_task_inactive` 等它下 CPU；本项目进入 stop 时把现场快照进持锁的连续 `CUserRegsStruct`，一致性由锁保证、与是否在 CPU 上无关。
- **全安全 Rust 的调试通路**：改寄存器、写别人内存、改控制流这三件内核里最易出内存安全漏洞的事，全程零 `unsafe`，危险性由所有权与类型系统在编译期约束。
- **字段策略收敛成单表**：x86 寄存器的字段级特殊处理用一张 `REG_RULES` 表声明一次、四条访问路径共查，替代 Linux 在读写两侧重列多遍的历史写法。

> 这几条不是「重新发明」，而是把同一套 ptrace 语义，重建到一个更安全、更分层的载体上。

---

## 第 11 页 — 2.2 ptrace-stop 主状态机：三类停止统一收敛

![主状态机](assets/04_state_machine.png)

- 生命周期：未被跟踪 → 建立关系 → **ptrace-stop（保存现场）** → wait 报告 → 恢复运行 → 命中下一次停止条件再回到 stop，或退出清理。
- 三种停止来源（信号停、系统调用停、事件停）**统一收敛到 `do_ptrace_stop()`**：同一抽象保存现场、记录 wait status、投 `SIGCHLD`、阻塞 tracee、resume 后回写。
- **与 Linux 的差异**：状态机与调度解耦——停止 / 恢复靠 tracee 自己进 stop 时快照、阻塞、唤醒，不依赖「等目标下 CPU」这类调度前提。

---

## 第 12 页 — 2.3 tracer 与 tracee 如何同步


![同步机制](assets/04b_sync.png)

- tracer（调试器线程）与 tracee（被调试线程）通过共享结构 TraceeStatus 同步，其中有一个原子标志和一把互斥锁。
![TraceeStatus 结构](assets/20260617-145625.jpeg)
- 原子标志 is_stopped 是 tracee 是否停在 ptrace-stop 的唯一依据：tracee 停下时置真并挂起，tracer 操作前据此确认其已停止、否则拒绝，恢复执行时置假并唤醒。
- 互斥锁 state 保护现场数据（寄存器快照、待投递信号、事件），两线程读写前都先持锁，避免并发竞争。

---

## 第 13 页 — 2.4 跨进程内存访问：在目标进程地址空间里直接读写

![内存访问](assets/07_mem_access.png)

- `ptrace PEEK/POKE` 与 `/proc/<pid>/mem` 走同一套底层读写原语，读写的都是「另一个进程」的内存。
- **不切换地址空间**：不把 CPU 页表切到目标进程，而是直接在它的地址空间里按页定位到物理页帧并拷贝；遇到缺页就主动触发一次缺页处理再重试。
- 整条跨进程读写都夹在统一的读写接口和权限检查边界内，安全可控。

---

## 第 14 页 — 2.5 x86-64 寄存器 ABI：字段级读写策略

![寄存器策略](assets/08_register_abi.png)

- **快照式访问**：tracee 陷入内核、进入 ptrace-stop 时，持锁把用户寄存器上下文复制成一份寄存器快照；tracer 持锁在快照上按字段修改，tracee 唤醒时再写回——作为 GDB `info registers` 的 ABI 基础。
- **按字段分级管控**：`rax..r15` 由 tracer 自由修改；`rip/rsp/fs/gsbase` 必须是用户地址；`rflags` 仅能写用户态可控位；`cs/ss/ds/es` 段寄存器只读、与 Linux 一致。
- **与 Linux 的差异**：「哪个字段要怎么校验」用单张 `REG_RULES` 策略表声明一次、读 / 写 / 按偏移四条路径共查同表，替代 Linux 在 `getreg`/`putreg`（及 32 位 compat）里重列多遍的历史写法，并以编译期断言防止表与结构体漂移。

---

## 第 15 页 — 2.6 恢复语义与信号四态机

![信号四态](assets/06_signal_states.png)

恢复请求：由 tracer 发送，可选择抑制（丢弃）原信号，或注入一个新信号。恢复语义 CONT（普通继续）、SINGLESTEP（设 TF 单步）、SYSCALL（开 syscall 跟踪）三选一。

状态如何被消费：

- tracer 通过 wait 消费 Pending：观察并报告，使其转为 Consumed。
- tracer 通过 GETSIGINFO 消费 Pending / Consumed / Injected：读取对应的 siginfo。
- tracee 在 resume 时通过 re-inject 消费 Pending / Injected：把信号重新投递给自己。

---

## 第 16 页 — 2.7 安全模型：统一鉴权 + Yama

![安全模型](assets/10_security_model.png)

- 统一决策链：**同进程 → UID/GID 匹配 → `CAP_SYS_PTRACE` → Yama LSM hook**。
- ptrace 与 procfs 区分 `Read/Attach`、`Fs/Real creds`，**避免 procfs 绕过**调试鉴权。
- Yama `ptrace_scope` 四档对各放行条件的影响（✓ 放行 / ✗ 拒绝；同进程恒放行）：

| Yama scope | 调用者是其祖先 | 具备 CAP_SYS_PTRACE | 仅 UID/GID 匹配 |
|---|:---:|:---:|:---:|
| 0 Disabled | ✓ | ✓ | ✓ |
| 1 Relational（默认） | ✓ | ✓ | ✗ |
| 2 Capability | ✗ | ✓ | ✗ |
| 3 NoAttach（设置后不可降级） | ✗ | ✗ | ✗ |

## 第 18 页 — 3.1 GDB / strace 实机演示

> **此处插入演示视频**（请在 PPT 中嵌入）：在 Asterinas 上真实运行 GDB 与 strace，内容即下方 CI 用例，已纳入持续集成、每次提交自动回归。

**GDB**：持续集成用 `gdb -batch` 调一段带断点的 C 程序，逐项校验输出：

- 命中断点，打印调用栈回溯（`#0 hello_world` → `#1 … in main`）
- 打印并修改变量与内存（读 `$1 = 1`、改 `*p = 4321`、内存校验通过）
- 读寄存器（`rip`、`rsp`），继续运行得到正确输出
- 全程**无任何 GDB warning**——说明寄存器/段 ABI 已对齐

**strace**：持续集成运行 `strace ls /tmp`，校验完整抓到系统调用序列（`execve()`、`getdents64()` 等）。

## 第 20 页 — 3.3 实现中的细节打磨

主线特性之外，还有一批小而必要的支撑改动（小 PR），它们决定了真实工具能否真正跑通：

- **`/proc/pid/mem` force-write**：允许写入只读代码页——这是写入 int3 软件断点的前提。
- **x86 GDT 插入空 KCODE32 槽**：把 USER_CS / USER_SS 调成 Linux 期望的 0x33 / 0x2b，消除 GDB 警告。
- **debug registers 读仿真 + personality 行为**：满足 GDB 的探测，又不放开硬件断点。
- **procfs 补全**：`/proc/[pid]/maps` 补全非 [stack] 条目以定位代码/库映射；`/proc/pid/auxv` 暴露辅助向量；`/proc/[tid]` 提供每线程视图。
- **`tkill` 系统调用与 Yama ptrace_scope**：补齐定向信号投递与调试安全边界。

## 第 22 页 — 4.1 总结与展望

**设计核心**　以 **ptrace-stop 状态机**为中心，把信号、异常、系统调用、wait、寄存器、跨进程内存、安全策略统一到一条 **Linux ABI 兼容**的调试路径。

**项目价值**　不止「能跑 GDB」——更为 RustOS 建立了**跨越多个内核子系统的调试能力骨架**，同时成为检验进程、内存、信号与安全模型正确性的**综合压力测试入口**。

**后续方向**

- 中途调试已运行进程：支持 `PTRACE_ATTACH / DETACH`。
- 调试多线程进程：fork/vfork/clone 的 event-stop。
- 支持 GDB watchpoint 观察点：x86 debug registers 真实读写。
- 寄存器扩展：`GETREGSET`、FP/SIMD。
- 跨架构推广：riscv64 / loongarch64。
